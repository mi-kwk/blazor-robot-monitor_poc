### AI が決めた設計（利用者が見直してよい点）

| 決めたこと | 理由 |
| --- | --- |
| 「Blazor Web App」の形（サーバーが画面のファイルも配信する）にし、画面はすべて WebAssembly で動かす | 1 つの URL で動き、起動するものが少ないため。あとで一部の画面を Server 方式にして比べることもできる（挙動確認の 3） |
| 事前レンダリング（サーバーで先に HTML を作る）を止めた | 事前レンダリングを使うと、画面の部品がサーバーでも一度動くため、接続用のサービスをサーバーにも用意する必要がある。最初は単純さを優先した |
| 模擬ロボット → サーバーは HTTP の POST、サーバー → 画面は SignalR | ロボットからの報告は送りっぱなしでよい。画面は、サーバーから届くものを即時に表示したいため |
| 状態は 1 秒ごとに全台分を送る。異常の一覧は変わったときだけ送る | 単純さを優先した。台数が増えたら、変わった分だけ送る方式を考える（挙動確認の 4） |
| 異常の判定はサーバーで行う | 画面を開いていなくても判定できるようにするため。画面を複数開いても結果がそろう |
| 起きる値と戻る値をずらした（電池 20%／25%、温度 60℃／55℃） | 境目で異常が出たり消えたりを繰り返さないため |
| 温度は 3 回続いたら異常にする | 一瞬の高い値で異常を出さないため |
| 判定に使う値は、すべて仮の値 | Notion の検討ページの案をそのまま使った |
| 履歴はサーバーのメモリにだけ持つ | 最小構成のため。再起動で消える（README の「確認中に気づいたこと」） |
| 接続が切れたら、つながるまで試し続ける（0 秒、2 秒、5 秒、以後 5 秒おき） | SignalR の既定では 4 回で諦めるため。監視画面は開きっぱなしで使う想定 |
| 最初の接続も、つながるまで自分で繰り返す | SignalR の自動の再接続は、一度つながった後に切れた場合しか働かないため |
| 部品集（MudBlazor など）は使わず、素の HTML と CSS で作った | Blazor そのものの書き方を学ぶため |
| 異常に「故障」を加えた（検討ページの案にはなかった） | 故障しても色が変わるだけで、異常の一覧に出なかったため |
| パッケージを 10.0.12 → 10.0.14 に上げた | ひな形の 10.0.12 に、既知の脆弱性の警告が出たため |
